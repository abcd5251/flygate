# The owner signs with their own QoreX wallet; the agent spends a deposited budget

Status: Accepted. Supersedes ADR-0001 and ADR-0002.

FlyGate must never hold an owner's keys, so in Live mode the owner signs in their own QoreX wallet and FlyGate's server keeps only its own keys (the agent and the demo merchant). QoreX gives a website one way to sign: `window.qorex.native.signAndBroadcast` with Cosmos messages. It refuses `signArbitrary`, EVM transactions, and every account-authority message (authenticators, spending rules, EVM windows). That rules out ADR-0002's design, which linked the agent key to the owner's account with a spending rule. So the money moves into the contract instead. In one wallet transaction the owner sends a `MsgSend` of the deposit to FlightEscrow and a `MsgCrossVMCall` to `openMandate(agent, mandate, deposit)`. diana's EVM lane refuses `funds` on a cross-VM call, and `openMandate` claims the balance that no one has accounted for yet. Both messages run atomically, so no one else can claim that balance. Measured on diana (`pnpm live:probe-crossvm`): the call's `msg.sender` is the owner's qor1 address as 0x, the send arrives first, and the account needs no EVM window. FlyGate's agent EOA calls `book()`. The contract checks the merchant's ML-DSA-87 quote signature and the mandate rules, then locks the price from the owner's budget. The agent can never send money anywhere else. Refunds go back to the budget, or straight to the owner once they called `closeMandate`, which also returns the unspent budget. FlyGate pays every gas fee except the owner's two wallet transactions. QoreX cannot sign a login message, so the authority comes from a random session key the owner's browser makes. Its hash is part of the on-chain `mandateHash`, and the server makes the agent act for an owner only on requests that present that key. Considered: keep signing on the server (this is custodial), and link the agent as an authenticator (QoreX refuses that from a website).
